20. PROBLEMAS TÉCNICOS ADICIONALES ENCONTRADOS EN LA REVISIÓN DE v1.6.18(Desarrollado)

20.1. LA CORRECCIÓN DE GEOMETRÍA PUEDE QUEDAR BLOQUEADA POR OTRAS VALIDACIONES
- BIN puede detectar que una ventana está en una posición o tamaño incorrectos, pero no llegar a corregirla si antes considera que existe conflicto de cuenta, perfil, URL, proceso o localizador.
- Esto puede explicar casos donde en un equipo la ventana se acomoda correctamente y en otro no, aun cuando la rutina se haya creado desde cero en ese mismo equipo.
- La corrección de geometría no debe depender innecesariamente de dimensiones de identidad que no sean necesarias para reconocer con suficiente certeza la ventana objetivo.

20.2. PROFILE N / DEFAULT TIENE DEMASIADO PESO EN LA IDENTIDAD DE CHROME
- `Profile 1`, `Profile 2`, `Default`, etc. son datos locales del equipo.
- El mismo correo puede estar en `Profile 2` en un PC y en `Profile 7` en otro.
- BIN no debe utilizar ese número/directorio como identidad portable.
- Debe considerarlo únicamente como localizador interno resuelto en el equipo actual.

20.3. BIN PUEDE DEDUCIR UNA CUENTA EQUIVOCADA A PARTIR DE UN PERFIL
- Si BIN no logra leer con certeza el correo de una ventana concreta, puede caer a la detección del perfil y posteriormente consultar Local State.
- Si el perfil asociado al proceso/ventana fue identificado incorrectamente, BIN puede terminar asignando una cuenta incorrecta a esa ventana.
- Cuando no exista certeza suficiente, BIN debe devolver “cuenta no identificada” y no fabricar una identidad mediante un fallback ambiguo.

20.4. UNA CUENTA/PERFIL DETECTADOS INCORRECTAMENTE PUEDEN QUEDAR PERSISTIDOS
- Una detección errónea puede terminar guardándose dentro de `contexto_despues`.
- En ejecuciones posteriores esa identidad aprendida puede convertirse en parte del contexto esperado.
- Esto puede hacer que el error parezca “pegado” a la rutina.

20.5. BIN PUEDE CONVERTIR UNA CUENTA NO REQUERIDA EN REQUISITO POSTERIOR
- Si una demostración o MicroPrompt no tenía una cuenta explícitamente registrada, una cuenta encontrada posteriormente no debe transformarse automáticamente en una obligación para futuras ejecuciones.
- Actualmente existe lógica que puede aprender y reutilizar cuenta/perfil.
- Debe conservarse la diferencia entre:
  * cuenta explícitamente requerida por el entrenamiento;
  * cuenta observada incidentalmente durante una ejecución.

20.6. LAS RUTAS ABSOLUTAS DE EJECUTABLES PUEDEN ROMPER PORTABILIDAD
- Una aplicación puede quedar identificada mediante una ruta absoluta como:
  `C:\Users\Usuario\AppData\...\programa.exe`
- En otro usuario o equipo la misma aplicación puede estar en otra ruta.
- Esto puede provocar un falso conflicto de identidad aun cuando el proceso/aplicación sea el correcto.
- La ruta exacta no debe ser identidad primaria para software portable entre usuarios.

20.7. UNA RUTA ABSOLUTA INCORRECTA PUEDE BLOQUEAR INDIRECTAMENTE LA GEOMETRÍA
- Aunque las coordenadas no están ligadas directamente a `C:\Users\<usuario>`, una ruta absoluta distinta puede hacer que BIN rechace primero la identidad de la ventana.
- Al rechazarla, puede no llegar a ejecutar la corrección de posición/tamaño.
- Por tanto, el problema de portabilidad de rutas puede manifestarse visualmente como un fallo de geometría.

20.8. LA VALIDACIÓN WEB SIGUE SIENDO DEMASIADO ESTRICTA
- URL, cuenta, perfil y otros campos pueden bloquear la identificación antes de que BIN intente corregir la ventana.
- Diferencias secundarias de URL no deberían impedir identificar una ventana si dominio/ruta útil y cuenta requerida coinciden.
- La comparación web debe mostrar y evaluar cada dimensión por separado.

20.9. LA TOLERANCIA DE GEOMETRÍA ES DEMASIADO RÍGIDA
- BIN utiliza una tolerancia fija pequeña para X, Y, ancho y alto.
- Un margen universal en píxeles no es suficiente para:
  * diferentes DPI;
  * escalado 100%, 125%, 150% o superior;
  * bordes de ventanas;
  * distintas versiones de Windows;
  * diferentes gestores/comportamientos de aplicaciones.
- Los márgenes deben ser visibles en diagnóstico y diseñarse de forma más adaptable.

20.10. LA VERIFICACIÓN DESPUÉS DE MOVER UNA VENTANA ES DEMASIADO RÁPIDA
- Después de ordenar un cambio de geometría, BIN vuelve a comprobar el estado tras una espera muy corta.
- En hardware lento, equipos bajo carga o con thermal throttling, Windows puede no haber terminado de aplicar el cambio.
- Debe sustituirse por verificación de estado con timeout y reintentos.

20.11. NO HAY TRATAMIENTO EXPLÍCITO SUFICIENTE DE DPI / ESCALADO
- La geometría adaptable existe, pero el código no modela de forma explícita las diferencias de DPI/escalado de Windows.
- Un equipo al 100% y otro al 125%/150% pueden producir diferencias legítimas.
- Antes de modificar las fórmulas de geometría debe instrumentarse y probarse el impacto real del DPI.

20.12. SETWINDOWPOS PUEDE FALLAR O TARDAR SIN UN DIAGNÓSTICO SUFICIENTE
- BIN necesita registrar claramente:
  * HWND objetivo;
  * geometría solicitada;
  * resultado de la llamada;
  * geometría observada después;
  * número de reintentos;
  * motivo de fallo si Windows no aplica el cambio.
- Actualmente un fallo o retraso puede convertirse en un error ambiguo.

20.13. LOS PARÁMETROS DE POSICIÓN/TAMAÑO AL ABRIR CHROME NO SON GARANTÍA
- Argumentos como `--window-position` y `--window-size` pueden no comportarse igual si Chrome ya está ejecutándose o reutiliza procesos/instancias.
- BIN no debe asumir que la ventana quedó correctamente ubicada solo porque envió esos parámetros.
- Debe esperar el HWND real, identificarlo y aplicar/verificar su geometría directamente.

20.14. IDENTIDAD, ESTADO Y GEOMETRÍA ESTÁN DEMASIADO ACOPLADOS
- Un error en URL, cuenta o perfil puede bloquear una corrección geométrica independiente.
- El supervisor debe separar:
  * identidad: qué ventana/aplicación es;
  * estado: qué contenido/URL/cuenta tiene;
  * geometría: dónde está y cuánto mide;
  * entorno local: perfil, ruta, DPI, monitor, privilegios.
- Cada dimensión debe poder informar su resultado sin contaminar innecesariamente las demás.

20.15. BIN NO DISTINGUE SIEMPRE “CUENTA DESCONOCIDA” DE “CUENTA INCORRECTA”
- Cuando no puede identificar una cuenta con certeza, algunos fallbacks pueden producir una cuenta inferida.
- Una identidad desconocida debe permanecer como desconocida.
- Sólo una cuenta realmente observada/resuelta con suficiente evidencia debe considerarse distinta o correcta.

20.16. LA BÚSQUEDA DE VENTANAS WEB PUEDE DESCARTAR UNA CANDIDATA DEMASIADO PRONTO
- Una ventana que potencialmente es la correcta puede ser marcada como conflictiva antes de intentar corregir URL, cuenta o geometría.
- La estrategia debe distinguir:
  * candidato imposible;
  * candidato probable pero corregible;
  * candidato confirmado.

20.17. EL DIAGNÓSTICO ACTUAL NO PERMITE SABER DE DÓNDE SALIÓ CADA IDENTIDAD
- Se necesita mostrar el origen de:
  * cuenta: UIA / Local State / otro;
  * perfil: UIA / `--profile-directory` / otro;
  * URL: barra confirmada / otro;
  * proceso y PID;
  * HWND;
  * ejecutable/localizador.
- Sin esta trazabilidad es difícil distinguir un error de detección de un error de comparación.

20.18. EL NIVEL DE PRIVILEGIOS DE WINDOWS PUEDE PRODUCIR FALLOS AMBIGUOS
- Una cuenta de Windows puede pertenecer al grupo Administradores y, aun así, BIN ejecutarse sin elevación.
- Si la aplicación objetivo está elevada y BIN no, Windows puede impedir determinadas interacciones/observaciones.
- Ese caso debe detectarse específicamente y no mostrarse como un simple conflicto de contexto, ventana o clic.

20.19. LA TAREA PROGRAMADA DE PREPARACIÓN USA RUNLEVEL LIMITED
- La programación de Windows actualmente usa `RunLevel Limited`.
- Esto confirma que no se puede asumir que BIN está elevado solo porque el usuario tenga una cuenta administradora.

20.20. EL FALLO OBSERVADO EN EL PORTÁTIL PUEDE TENER UNA CAUSA COMÚN
- Los síntomas:
  * cuenta de Chrome incorrecta;
  * URL correcta;
  * ventana que no se acomoda;
  pueden provenir de un mismo fallo de identificación previa.
- Si BIN identifica mal la cuenta/perfil, puede marcar la ventana como conflicto y no llegar a aplicar su geometría.
- Esta hipótesis debe comprobarse con el diagnóstico completo antes de modificar las fórmulas de coordenadas.
